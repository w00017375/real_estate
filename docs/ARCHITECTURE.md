# Архитектура парсера

## Модули

```text
main.py                     универсальный запуск конвейера
parse_platform.py           выбранные платформы в JSON без SQLite
seller_deduplication.py     локальная дедупликация и статус продавца
core/
  config.py                 лимиты и пути выходных файлов
  normalization.py          очистка чисел, текста, телефона и отпечатков
  seller_metadata.py        метаданные и признаки профилей продавца
  deduplication.py          удаление дублей внутри запуска и между запусками
  seller_analysis.py        прежняя модель оценки (не вызывается конвейером)
  pipeline.py               формирование публичного объекта результата
sources/
  base.py                   контракт ListingSource
  olx.py                    только OLX: URL, Playwright, селекторы и параметры
  etagi.py                  адаптер каталога Etagi
  uybor.py                  адаптер каталога Uybor и авторизованной сессии
  realting.py               адаптер Realting на основе housing_source_data
standalone_parsers/         автономные и raw-парсеры отдельных платформ
tools/                      локальные миграции и генераторы документации
output_json/<platform>/     JSON-результаты, разделённые по источникам
docs/                       README, архитектура, UML и матрица данных
storage/
  json_store.py             JSON-экспорт
  sqlite_store.py           универсальная реляционная SQLite-база
```

`core` и `storage` не импортируют OLX и Playwright. Всё, что зависит от
верстки, языка параметров или пагинации конкретного сайта, должно находиться
в его модуле внутри `sources`.

## Канонический контракт источника

Метод `collect(limit=None)` каждого источника возвращает список следующего
вида. `None` означает обход каталога до последней доступной страницы:

```python
{
    "source": "site_name",
    "id": "platform-id",
    "title": "...",
    "price": 500,
    "currency": "USD",
    "url": "https://...",
    "published_at": "2026-08-28T14:30:00+05:00",
    "_description": "внутренний текст для выбора лучшего дубликата",
    "housing": {
        "city": "Ташкент",
        "district": "Чиланзар",
        "rooms": 2,
        "total_area_m2": 55.0,
        "floor": 3,
        "floors_total": 9,
        "furnished": True,
        "commission": False,
    },
    "amenities": ["Интернет"],
    "nearby": ["Парк"],
    "seller": {
        "name": "...",
        "phone": "+998901234567",
        "profile_url": "https://...",
        "is_official_seller": False,
        "official_complex_name": None,
    },
}
```

Профиль продавца отдельно не открывается. Для каждой напрямую обработанной
публикации создаётся отдельная сырая строка `sellers`. `_description`
используется как содержимое текущей карточки и не участвует в оценке продавца.

## Дедупликация и оценка продавца

Основной парсер не выполняет оценку и дедупликацию продавцов. После полного
парсинга отдельно запускается `seller_deduplication.py`. Он локально:

- оставляет в телефоне только цифры ASCII;
- не изменяет строки с `phone IS NULL`;
- удаляет полные дубли seller с перепривязкой `listings.seller_pk`;
- формирует `seller_duplicates` по номеру, площадке и URL профиля;
- записывает в `phone_listing_count` число объявлений на номер;
- присваивает `seller_status = realtor` при 3 и более объявлениях,
  иначе `seller_status = owner`.

Поля `seller_type`, `sellers_type`, `realtor_probability`,
`assessment_comment`, `active_rent_listings`, `active_sale_listings`,
`unique_listing_count`, `distinct_housing_listings` и
`profile_scan_complete` удалены из таблицы `sellers`.

В `listings`, `housing` и связанных таблицах строка
создаётся только для объявления, страницу которого адаптер открыл напрямую и
полностью обработал. Карточки со страницы продавца могут временно повысить
счётчик активности, но в SQLite не сохраняются.

## Наблюдение за объявлениями

Повторная встреча того же платформенного ID или URL обновляет существующую
строку `listings`, а не создаёт новую. `first_seen_at` остаётся неизменным;
`last_seen_at` и `last_checked_at` отражают последнюю успешную обработку и
проверку. При изменении данных заполняется `last_changed_at` и создаётся снимок
в `listing_history`. `current_price` синхронизирован с совместимой колонкой
`price`, а `previous_price` хранит непосредственно предшествующее значение.

API карты группирует публикации в физические объекты жилья консервативным
взвешенным сопоставлением адреса/ЖК/координат, комнат, площади, этажа,
этажности и доступных данных продавца. Платформа не входит в ключ, а разные
продавцы не считаются конфликтом. Исходные строки `listings` при этом не
удаляются: карточка получает список `offers` с URL и ценой каждой площадки.

OLX-адаптер распознаёт официальный профиль ЖК по адресу вида
`https://<название>.olx.uz/home/`. В таком случае продавец получает
`is_official_seller = true`. Домен используется только для подтверждения
статуса, а `official_complex_name` берётся из имени продавца: текст начиная с
фразы `на OLX с` отбрасывается. Обычные профили на `www.olx.uz` не помечаются.

## Realting

`RealtingSource` открывает каталог `https://realting.uz/property-to-rent`,
берёт ссылки вида `/property-to-rent/<id>` и открывает каждую публикацию.
Поля адаптера соответствуют ключам JSON из
`standalone_parsers/realting_publication_raw_json.py`:
`ID`, `Заголовок`, `Цена`, `Местонахождение` и вложенным группам
`Характеристики объекта`. Из строки `singleMarker` извлекаются координаты;
для аренды цена используется как `monthly_rent`, а `price_per_m2` считается
общим конвейером.

В исходном raw-JSON публикации контакты агентства не были выделены отдельным
ключом; живой блок объявления содержит профиль агентства и защищённый телефон,
которые извлекает `RealtingSource`. Телефон из JSON-LD принадлежит организации
Realting, поэтому в `sellers` он намеренно не записывается. Также в источнике нет точного адреса улицы/дома, даты публикации,
типа здания, признака новостройки, ЖК, фундамента и мебели; соответствующие
колонки БД остаются `NULL`. В текущей схеме отдельно не предусмотрены полное
описание, жилая площадь, количество ванных, метро и фотографии. Они остаются
доступны в raw-JSON скрипта, но не подменяются данными организации сайта.

`standalone_parsers/realting_agencies.py` отдельно обходит `/agencies`,
сохраняет профиль агентства
по ключу `profile:https://realting.uz/agencies/<slug>` и записывает
`source_seller_role = 'agency'`. Итоговый `seller_status` вычисляется общим
локальным постпроцессором. Ссылки публикаций экспортируются в
JSON как реестр, но не создают строки `listings`, пока объявление не открыто и
не обработано полностью. `RealtingSource` извлекает тот же профиль агентства
из карточки объявления, поэтому его `seller_pk` связывается с заранее
импортированной строкой `sellers`; телефон и профиль получают источник
`realting`.

## Добавление нового сайта

1. Создать `sources/new_site.py`.
2. Реализовать класс-наследник `ListingSource` с `name`, `start_url` и
   `collect(limit=None)`.
3. Преобразовать оригинальные поля сайта в канонический контракт выше.
4. Передать адаптер в `run_source`:

```python
from core.config import AppConfig
from main import run_source
from sources.new_site import NewSiteSource

run_source(NewSiteSource(), AppConfig())
```

Оценку риэлтора, дедупликацию, JSON и схему базы для нового источника менять
не требуется.
