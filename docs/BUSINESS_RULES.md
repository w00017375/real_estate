# Методика определения дублей и внутренних расчётов

Документ описывает фактические правила текущей версии проекта на бизнес-языке: что считается повтором, какие записи сохраняются или удаляются и как рассчитываются производные показатели.

## 1. Порядок обработки данных

1. OLX, «Этажи», Uybor, Realting и Realt24 опрашиваются параллельно.
2. Из каждого источника повторно открываются как новые, так и уже известные публикации. При `--limit 7` обрабатываются первые семь карточек каталога независимо от того, есть ли они в базе.
3. Данные источников приводятся к единой структуре.
4. Объявления сортируются от самой новой даты публикации к самой старой. Объявления без даты помещаются в конец.
5. Объявления и связанные данные сохраняются в SQLite.
6. Объединение повторных продавцов и их классификация выполняются после парсинга отдельным локальным скриптом `seller_deduplication.py`.

## 2. Уже известное объявление

Объявление считается уже известным, если выполняется хотя бы одно условие:

- на той же платформе совпал платформенный идентификатор объявления;
- совпала нормализованная ссылка объявления.

Перед сравнением ссылки удаляются:

- параметры после `?`;
- фрагмент после `#`;
- завершающий `/`.

Регистр протокола и домена не учитывается. Например, эти ссылки считаются одной публикацией:

```text
https://example.uz/listings/123/?utm_source=test#gallery
https://example.uz/listings/123
```

Если публикация уже известна, новая строка `listings` и новая строка продавца не создаются. Детальная карточка обновляет текущую цену, описание, статус и доступные характеристики жилья. Пустое значение источника не стирает уже сохранённое непустое значение.

Перед самой записью выполняется повторная проверка по сочетанию «платформа + ID» и по URL. Она защищает от одновременной записи одного объявления параллельными процессами.

Каждая успешная обработка обновляет `last_seen_at` и `last_checked_at`. При фактическом изменении обновляется `last_changed_at`, а снимок добавляется в `listing_history`.

## 3. Дубликат объявления во время парсинга

Существование публикации определяется по сохранённому платформенному ID или
нормализованному URL. При совпадении обновляется эта же строка. Если цена,
описание, статус или характеристика изменились, создаётся запись истории;
неизменённая проверка историю не раздувает.

Отдельные публикации одного физического жилья объединяются для карты по
взвешенному сравнению города, района, адреса или ЖК, координат, комнат,
площади, этажа и этажности. Телефон и имя продавца служат дополнительными
признаками, но их различие не запрещает объединение: один объект могут
разместить собственник и несколько риэлторов. Название платформы в оценке
сходства не участвует. При недостатке сильных адресных признаков карточки не
объединяются, чтобы не склеить разные квартиры с одинаковой планировкой.

## 4. Сохранение продавцов

Во время парсинга продавец сохраняется как сырой факт конкретного объявления. Его профиль дополнительно не открывается.

- Один найденный телефон создаёт одну запись продавца.
- Несколько телефонов создают отдельную запись продавца на каждый номер.
- Все телефоны связываются с одним объявлением через `listing_sellers`.
- Первый найденный телефон считается основным и указывается через `listings.seller_pk`.
- При отсутствии телефона продавец всё равно сохраняется.

Временный `identity_key` равен URL объявления. Если URL отсутствует, используется сочетание платформы и платформенного ID. Этот ключ различает сырые факты до постобработки и не означает уникального человека или компанию.

## 5. Дедупликация продавцов

`seller_deduplication.py` работает только с локальной SQLite-базой и не обращается к сайтам.

### Нормализация телефона

Из каждого непустого телефона удаляются пробелы, `+`, скобки, дефисы и другие знаки. Остаются только цифры `0–9`.

```text
+998 (90) 123-45-67 → 998901234567
```

Значения `NULL` не изменяются и не участвуют в телефонной дедупликации. Нераспознаваемая строка после очистки может стать пустой и также исключается из расчётов.

### Полный дубль продавца

После нормализации телефона полным дублем считаются записи с одинаковой
комбинацией:

- URL профиля продавца;
- платформа;
- номер телефона.

Имя и остальные поля продавца в ключ не входят. Значение `NULL` у URL
участвует в сравнении как обычное значение: две строки без URL считаются
дублями, если у них также совпадают платформа и непустой телефон. Строки с
`NULL` или пустым телефоном не удаляются.

При полном совпадении:

1. Остаётся строка с наименьшим `seller_pk`, то есть самая ранняя.
2. Все объявления и зависимые записи перепривязываются к ней.
3. Лишняя строка удаляется.
4. В конце проверяется целостность внешних ключей.


### Один телефон у разных записей

Если после удаления полных дублей один номер остаётся у нескольких различающихся продавцов, строки не удаляются. Их снимок переносится в `seller_duplicates` по сочетанию:

- телефон;
- платформа;
- URL продавца.

Для комбинации сохраняются первый `seller_pk` и количество повторений. `seller_duplicates` полностью пересобирается при каждом запуске и показывает текущее состояние базы.

## 6. Определение типа продавца

Статус рассчитывается по нормализованному номеру телефона на основании всех платформ.

```text
0–2 уникальных объявления → owner
3 и более                → realtor
```

Считаются разные `listing_pk`, поэтому повторная связь с одним объявлением не увеличивает показатель. Результат записывается во все строки с данным номером:

- `seller_status` — `owner` или `realtor`;
- `phone_listing_count` — число уникальных объявлений на номер.

Для продавцов без номера эти поля остаются `NULL`.

Это вероятностная бизнес-эвристика, а не подтверждённый юридический статус. Частный собственник с тремя объектами будет отнесён к `realtor`, а начинающий риэлтор с одним объявлением — к `owner`.

## 7. Расчёты по жилью

### Месячная аренда и валюта

Для аренды используется специальная цена жилья. Если источник не передал её отдельно, берётся цена объявления. Аналогично выбирается валюта аренды.

### Цена квадратного метра

Если источник не передал готовое значение, применяется формула:

```text
цена за м² = месячная арендная плата / общая площадь
```

Результат округляется до двух знаков. Расчёт не выполняется при отсутствии цены или площади либо при нулевой площади.

### Адрес

Город и район приводятся к единому написанию для известных вариантов названий. Район хранится отдельно от точной адресной строки.

Поле `street` составляется из доступных частей в порядке:

1. зона, массив или квартал;
2. улица;
3. номер дома.

Одинаковые части не повторяются. Если структурированных частей нет, используется общий адрес источника.

### Удобства и места рядом

Каждое уникальное значение хранится один раз в справочнике. Объявление связывается с ним через промежуточную таблицу. Одна характеристика не может быть дважды привязана к одному объявлению.

### Изображение

Из списка выбирается первая корректная ссылка, начинающаяся с `http://` или `https://`. В текущей базе хранится одно основное изображение на объявление. Если подходящей ссылки нет, строка изображения не создаётся.

## 8. Даты, порядок и статус публикации

Распознанные даты переводятся в часовой пояс Ташкента и сохраняются в формате:

```text
YYYY-MM-DD HH:MM:SS
```

- `published_at` — дата публикации, если источник позволил её получить;
- `first_seen_at` — время первоначального сохранения новой публикации.
- `last_seen_at` — последняя успешная обработка доступной карточки;
- `last_checked_at` — последняя попытка проверки URL или повторного парсинга;
- `last_changed_at` — последнее обнаруженное изменение любых отслеживаемых данных.

`current_price` хранит актуальную цену, `previous_price` — непосредственно
предшествующую цену. Совместимая колонка `price` всегда синхронизируется с
`current_price`. В `listing_history` сохраняются начальный снимок и только
фактические изменения цены, описания, статуса или данных жилья.

При первоначальной записи статус определяется по приоритету:

1. Явное значение `active` или `closed` от источника.
2. Наличие URL в переданном списке активных или закрытых публикаций.
3. `active` по умолчанию.

Ежедневный ручной `live_scanner.py` проверяет URL всех строк со статусом
`active`. Значение меняется на `closed` только при HTTP 404/410 или при явном
сообщении площадки о снятом объявлении. Ошибка сети, тайм-аут, CAPTCHA,
HTTP 403/429 или сбой сервера считаются неоднозначным результатом и не меняют
статус. Отсутствие карточки на первой странице каталога само по себе также не
означает закрытие.

После проверки актуальности каталоги источников просматриваются параллельно в
порядке от новых публикаций к старым. Известные карточки не являются границей:
они повторно обрабатываются, чтобы обнаружить цену и другие изменения. Без
лимита обход продолжается до конца доступного каталога.

## 9. Учёт запусков

Каждый пакет обработанных данных получает запись в `scrape_runs`. В ней фиксируются время, источник, адрес каталога и установленный лимит. Значение лимита `0` означает, что явное ограничение не задавалось.

`scrape_run_listings` связывает запуск с каждой полностью обработанной карточкой — как новой, так и уже известной. Неполные карточки и каталожные строки, которые не открывались напрямую, туда не добавляются.

## 10. Защита записи в базу

Перед парсингом проверяется возможность записи в SQLite. При временной блокировке выполняется до трёх попыток с увеличивающейся паузой.

Если файл удерживается DB Browser, SQLite Viewer или другим процессом, запуск завершается с сообщением о блокировке. Незавершённая транзакция откатывается, поэтому частично записанный пакет не считается сохранённым.

## 11. Матрица решений

| Ситуация | Результат |
|---|---|
| Совпал ID на той же платформе | Обновляется существующая строка и время проверки |
| Совпала очищенная ссылка | Обновляется существующая строка и время проверки |
| Цена изменилась | Предыдущая цена переносится в `previous_price`, новый снимок пишется в историю |
| Данные не изменились | История не пополняется |
| Один объект размещён по разным URL или продавцами | Публикации сохраняются отдельно, но на карте объединяются в одно жильё с несколькими предложениями |
| Нет телефона | Продавец сохраняется, телефонные расчёты не выполняются |
| В объявлении несколько телефонов | Каждый контакт сохраняется и связывается с объявлением |
| Совпали URL продавца, платформа и телефон | Остаётся самая ранняя строка, связи переносятся |
| Совпал телефон, но остальные данные отличаются | Строки остаются и отражаются в `seller_duplicates` |
| На номер приходится 3+ объявлений | `seller_status = realtor` |
| На номер приходится менее 3 объявлений | `seller_status = owner` |
| Нет явного статуса публикации | Используется `active` |
| URL ответил 404/410 или показал явный текст о закрытии | Статус меняется на `closed` |
| URL вернул CAPTCHA, 403/429, тайм-аут или ошибку сети | Статус не меняется |
| Нет площади или цены | Цена за м² не рассчитывается |
| В публикации несколько изображений | Сохраняется первое корректное |

## 12. Ограничения методики

- Совпадение телефона и характеристик жилья не гарантирует, что это один физический объект.
- Разное написание адреса или округление площади может скрыть фактический дубль.
- Общий номер агентства объединяет статистику нескольких сотрудников.
- Продавцов без телефона нельзя надёжно связать между платформами текущим методом.
- Повторное открытие известных карточек увеличивает время полного обхода, но
  позволяет отслеживать цену, описание и другие изменения.
- Объединение жилья консервативно: без адреса, ЖК или близких координат
  одинаковые по площади и комнатам публикации останутся раздельными.
- Порог в три объявления следует проверять на размеченной выборке до использования в качестве окончательного бизнес-решения.
